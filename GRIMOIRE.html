The five golden rules (memorize these first)

  1. UI = f(state). You never “change the screen”. You change data, and Flutter re-runs build() to describe the new screen.
  2. Widgets are blueprints, not objects on screen. They are cheap, immutable, and thrown away every rebuild.
  3. Constraints go down, sizes go up, the parent sets the position. All of Flutter layout is this one sentence.
  4. The database is the source of truth. Screens watch it with a Stream; when a row changes, the screen updates by itself.
  5. Never block the UI thread. Slow work (disk, network, big maths) is async or runs in an isolate, so the app stays at 60+ frames per second.

0.7 Fix the admin-lock hang done OS

Running Flutter as Administrator made its cache lock files admin-owned, so normal runs waited forever. Never run Flutter as Administrator.

  • Flutter uses a lock file so two flutter commands don't update the cache at once.
  • Files created by an admin process belong to admin; a normal process can't take/delete them.
  • Fix: grant permissions (icacls) and delete stale locks.

The OS concepts underneath

Mutual exclusion (mutex): a lock file is the simplest mutex across processes. Process A holds the lock → process B waits. If the lock can never be released (A died, or B lacks permission), B waits forever: a hang that looks like a deadlock.

Ownership & ACLs: on Windows every file has an owner and an Access Control List saying who can read/write. Elevated (admin) processes create files owned by Administrators; your normal user then gets “access denied” silently inside Flutter's lock logic.

The secret of Flutter: three trees

You only write the first tree. Flutter keeps the other two for you. This is why rebuilding is cheap.

Widget treeblueprints · immutable · created fresh on every build()
Element treethe living tree · long-lived · holds State · = BuildContext
RenderObject treedoes layout (sizes) and paint (pixels)

Widget = the order slip (“a blue Text saying 5”). Thrown away after each build.

Element = the waiter who keeps the table. When a new slip arrives, it compares: same type and key? Then just update the existing RenderObject instead of building a new one.

RenderObject = the kitchen. Measures sizes, positions children, paints.

Your State object lives on the Element, so it survives rebuilds; that's why _counter isn't lost when build() runs again.

Each frame: build (widgets) → layout (sizes) → paint (layers) → composite (GPU). Budget: about 16 ms at 60 Hz.

1.3 StatelessWidget, build(), constructors done

A stateless widget only depends on its constructor inputs; build() returns what it looks like.

  • const MyApp({super.key}); named parameters in { }, required for mandatory ones.
  • Fields are final; widgets are immutable.
  • const widgets are created once at compile time and reused → fewer rebuilds.
class RoomTile extends StatelessWidget {
  const RoomTile({super.key, required this.name, this.icon = Icons.door_front_door});
  final String name;      // required
  final IconData icon;    // optional with default

  @override
  Widget build(BuildContext context) {
    return Card(child: ListTile(leading: Icon(icon), title: Text(name)));
  }
}
// use: RoomTile(name: 'Owlery')

this.name in a constructor = “assign the argument straight to the field” (Kotlin's val in the primary constructor). super.key forwards the key to the parent class. Key = identity hint so Flutter can tell list items apart when they move.

@override = “I'm replacing the parent's method”, same as Java.

Forgetting const isn't an error, just a missed optimisation; the linter will remind you.

1.5 StatefulWidget and State doing now

A widget that can change: the widget holds the settings, a separate State object holds the changing data (like _counter).

  • Two classes: MyHomePage (immutable config) + _MyHomePageState (mutable, long-lived).
  • createState() links them; the State reads config via widget.title.
  • Underscore _ = private to this file.

Why split into two classes?

Widgets are rebuilt constantly and must be immutable. But a counter must remember. So the remembering part lives in a State object stored on the Element, which is long-lived. When the parent rebuilds and passes a new MyHomePage(title: …), the same State is kept and just gets a new widget.

2.8 Sorting logic todo DSA

Each answer adds points to houses; the highest total wins (argmax), with a rule for ties.

  • Accumulate into Map<House,int>, then pick the max entry.
  • Pure function, no Flutter imports → easy unit test (2.24).
  • Time O(questions × houses), trivial.
House sort(List<Answer> chosen) {
  final scores = {for (final h in House.values) h: 0};
  for (final a in chosen) {
    a.points.forEach((house, pts) => scores[house] = scores[house]! + pts);
  }
  // argmax; ties broken by enum order (or ask a tie-breaker question)
  return scores.entries.reduce((best, e) => e.value > best.value ? e : best).key;
}

4.5 $1 Unistroke Recognizer todo DSA · geometry

Your own algorithm: resample, rotate, scale, translate the stroke, then compare with templates by average point distance.

  • 1 Resample to N = 64 evenly spaced points (speed of drawing stops mattering).
  • 2 Rotate so the “indicative angle” (centroid → first point) is 0°.
  • 3 Scale to a 250×250 box · 4 Translate centroid to (0,0).
  • Match: average distance to each template, refined by golden-section search over ±45°; score = 1 − d / (½·√(2·250²)).
After these four steps, the same shape drawn big/small, fast/slow, tilted or shifted looks almost identical as 64 numbers.
double pathDistance(List<Offset> a, List<Offset> b) {
  var d = 0.0;
  for (var i = 0; i < a.length; i++) { d += (a[i] - b[i]).distance; }
  return d / a.length;
}
// recognize: for each template t → best = min over angles θ of pathDistance(rotate(points, θ), t)
//           score = 1 - best / (0.5 * sqrt(2 * 250 * 250)); accept if score > ~0.8

Complexity: O(N · T · k) where T templates, k golden-section iterations (~10). Tiny. Limitations: one stroke only; can't tell a circle drawn clockwise from anticlockwise unless you store both; rotation-invariant so it can't tell “6” from “9” (option: disable rotation). 5.2 SM-2 algorithm todo DSA

Calculates when to show a memory next, based on how well you remembered it (quality 0–5).

  • Fail (q < 3): repetitions = 0, interval = 1 day.
  • Pass: interval = 1, then 6, then previous × EF; repetitions + 1.
  • EF' = EF + (0.1 − (5−q)(0.08 + (5−q)·0.02)), never below 1.3.
class Review { const Review(this.ease, this.interval, this.reps); final double ease; final int interval; final int reps; }

Review sm2(Review r, int q) {                 // q: Again=1, Hard=3, Good=4, Easy=5
  var ease = r.ease + (0.1 - (5 - q) * (0.08 + (5 - q) * 0.02));
  if (ease < 1.3) ease = 1.3;
  if (q < 3) return Review(ease, 1, 0);
  final interval = switch (r.reps) { 0 => 1, 1 => 6, _ => (r.interval * ease).round() };
  return Review(ease, interval, r.reps + 1);
}

7.3 Server database + API todo DBMS · CN

A PostgreSQL schema mirroring the app's tables, plus endpoints to push and pull changes.

  • Every table gets user_id (whose data) and server_seq (a global ever-increasing change counter).

7.6 Offline queue todo CN

Changes made offline wait in a queue (outbox) and are sent when the internet returns, with retries.

  • Outbox pattern: the data write and the queue insert happen in one transaction.
  • Retry with exponential backoff + jitter: 1 s, 2 s, 4 s, 8 s… plus randomness.
  • Idempotency: each change has an id; the server ignores duplicates, so retrying is safe.

Why the same transaction? If the app crashes between “save memory” and “queue it”, the change would never sync. One transaction = both or neither. Why idempotent? A request can succeed on the server but the response gets lost; the phone retries; the server must not apply it twice.

  for (e in edges) { pull(e.from, e.to); }                                   // d² / k, together
  for (n in nodes) { n.pos += clamp(n.force, temperature); n.force = zero; }
  temperature *= 0.97;                                                       // cool down (simulated annealing)
}

Algorithm: Fruchterman–Reingold. Run it in an isolate for big graphs. Tapping a node opens that memory; colour nodes by tag.

8.12 End-to-end encryption todo Security

Synced data encrypted on the device so even the server can't read it.

  • Key derived from a passphrase with a slow KDF (Argon2id / PBKDF2 with salt).
  • Encrypt before push, decrypt after pull; the server stores ciphertext only.
  • Trade-off: server-side search is impossible; lose the passphrase = lose the data (offer a recovery key).

Usually a random data key encrypts everything, and the passphrase-derived key only encrypts (wraps) the data key. Changing the passphrase then re-wraps one small key instead of re-encrypting everything. Metadata (timestamps, sizes) still leak; that's a known limit of E2EE.

  • Version the export format ("format": 1) so future imports understand old files.

8.14 Ask the Pensieve todo AI/ML

  • Embedding = a list of numbers (vector) that captures meaning; similar meaning → nearby vectors.
  • Similarity = cosine of the angle between vectors.
  • RAG: retrieve the most similar chunks, give them to a language model as context, ask it to answer from them.

FTS (2.22) matches words; embeddings match meaning (“stag” finds “Prongs”). Pipeline: split memories into chunks (~200–500 words) → embed each once (store vector as BLOB) → at query time compare. 9.2 App signing todo Security

A release keystore proves updates come from you. Back it up, keep it out of Git.

  • Create once: keytool -genkey -v -keystore upload-keystore.jks -keyalg RSA -keysize 2048 -validity 10000 -alias upload.
  • android/key.properties (git-ignored) holds the path and passwords; build.gradle.kts reads it.
  • With Play App Signing, Google holds the real app key; you keep an upload key.

Android only installs an update if it's signed with the same key as the installed app. Lose the key (without Play App Signing) = you can never update the app again. Digital signatures: private key signs, public key (inside the certificate) verifies.
